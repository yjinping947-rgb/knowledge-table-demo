# 知识拼桌核心流程 PRD

版本：V2.3
基于：V2.2 修订
Demo 话题：年轻人该不该裸辞？
文档状态：核心流程收敛版 / 上下文与席位契约补充版

## 1. 本次修订结论

V2.2 的产品方向保留：先听两个有依据的不同观点，再由用户选择一个真实冲突进行碰撞，最后留下用户自己的思考轨迹。

V2.3 重点修订四件事：

1. 明确每次 Agent 调用必须携带的话题、席位、用户问题和本桌上下文；
2. 将“检索、生成、校验”拆成三个独立能力，禁止用原文摘录替代回答；
3. 将席位身份作为全链路不变量，防止席位串位和旧请求覆盖；
4. 收敛 Demo 主路径，第三席改为可选增强，不得阻塞结果生成。

核心闭环仍然是：

> 听两个真实观点 → 选择当前倾向 → 选择碰撞点 → 一轮质疑—回应 → 校准隐藏分歧 → 留下思考轨迹。

第三席负责提供可选的新视角，不是完成讨论的必要条件。

## 2. 产品定义

知识拼桌不是多篇回答并排展示，也不是多个 Agent 自由聊天。

产品先让用户听懂两个有真实知识依据、观点不同的席位。用户可以分别追问，但追问必须围绕当前席位和用户最新情境生成新的回答。两席表达完成后，用户记录当前倾向，并从已经发生的内容中选择一个值得继续讨论的具体问题。

两席围绕该问题完成一次“质疑—回应”。AI 从实际碰撞中提出隐藏分歧候选，由用户确认、修改或拒绝。用户可以进一步探索第三知识视角，也可以直接结束并生成讨论地图与灵魂金句。

AI 不替用户做决定，也不得把推测出的心理变化写成用户真实结论。

## 3. 角色与席位

| 角色 | 稳定 ID | 职责 |
| --- | --- | --- |
| 第一席·行动派 | `action` | 关注健康、不可逆损失和及时止损，同时说明行动边界 |
| 第二席·现实派 | `realist` | 关注现金流、家庭责任、替代方案和风险承受能力 |
| 第三席·条件视角 | `conditional` | 从用户确认的隐藏分歧中提供新的判断框架；可不入桌 |
| 用户 | 独立角色 | 听取、追问、选择、补充条件、校准和表达离桌理解 |
| 主持人 | `director` | 控制节奏、解释阶段、指出讨论结构，不替用户裁决 |
| 知识系统 | — | 检索、标注和提供知乎来源 |

用户不是“第四席”，不参与席位 Agent 编排。

## 4. 修订后的核心流程

```text
进入话题
  ↓
第一席发言
  ├─ 可选：追问第一席 → 回到第一席锚点
  ↓
第二席发言
  ├─ 可选：追问第二席 → 回到第二席锚点
  ↓
记录首次倾向（三选一）
  ↓
从已发生内容中选择碰撞点
  ├─ 可选：补充一次个人条件
  ↓
另一席质疑 → 原席位回应
  ↓
AI 提出隐藏分歧候选
  ↓
用户确认 / 修改 / 拒绝
  ↓
直接整理结果
  └─ 可选：探索第三视角 → 邀请入桌或跳过
  ↓
用户表达离桌时理解（可跳过）
  ↓
讨论地图 + 灵魂金句 + 来源索引
```

最短路径不应被第三席、自由追问或额外辩论阻塞。

## 5. 用户体验要求

### 5.1 听：两席依次发言

每席固定展示：

- 核心观点；
- 主要理由；
- 适用边界；
- 席位名称与稳定身份；
- 参考知乎来源；
- “举手追问”入口。

V2.3 要求真正存在第一席、第二席两个阶段：

```text
intro → first-seat → second-seat → tendency
```

每席追问结束后必须显示回归锚点，例如：

> 刚才你追问了行动派关于家庭责任的判断。现在继续听现实派，看看它如何处理同一个条件。

### 5.2 追问：针对当前席位和最新情境回答

追问是可选支线，默认每席支持一轮；结束后回到主流程。

追问回答必须：

1. 直接回应用户最新问题或新增情境；
2. 保持当前席位立场；
3. 说明原有判断是否需要调整；
4. 给出边界、触发条件或不确定性；
5. 提供正确席位的参考来源；
6. 来源不足时明确说明，不强行补齐。

禁止将检索到的某条原文前 260 个字符直接作为回答。

### 5.3 选：记录首次倾向

两席完成后只展示三个选项：

- 更接近第一席；
- 更接近第二席；
- 暂时无法判断。

“两边都有道理”“两边都没说到重点”可作为离桌表达或补充反馈，不放入首版必选项。

### 5.4 碰：选择一个真实碰撞点

碰撞点必须来自以下至少一项：

- 两席已经表达的判断；
- 用户对任一席的真实追问；
- 用户补充的个人条件；
- 两席之间已经显现出的矛盾。

首版允许使用“预置合格碰撞点 + 用户补充问题”。只有当系统能基于完整上下文稳定生成并提供证据时，才对外承诺“动态生成碰撞点”。

合格碰撞点是具体问题，例如：

- 三个月存款够不够支撑裸辞？
- 继续留下本身是不是一种风险？
- 哪种损失更难恢复？

不合格碰撞点：健康问题、经济问题、裸辞风险等泛化标签。

用户可以选择“都不是，我想碰……”并输入一个问题。

#### 5.4.1 拖动触发规则

用户从 AI 动态生成的 2—3 个候选中选择一个后，该碰撞点以卡片形式进入可拖动状态。用户将碰撞点卡片拖到两席中间，才确认选择并触发本轮观点碰撞。

- 仅点击卡片不会触发质疑—回应；
- 卡片未拖入两席中间时，允许重新选择；
- 拖动成功后，卡片固定在两席之间，并展示正在碰撞的状态；
- 拖动只负责触发碰撞，不直接生成第三席；
- 第三席只能在真实碰撞完成、隐藏分歧被用户确认后生成。

核心链路固定为：

> 选碰撞点 → 拖到两席中间 → 触发质疑—回应 → 提取隐藏分歧 → 用户确认 → 生成第三席预览。

### 5.5 碰撞：拖动后固定一轮质疑—回应

规则：

1. 只有碰撞点卡片拖到两席中间后，才触发本轮碰撞；
2. 用户选中哪一席的判断，另一席先提出质疑；
3. 质疑必须指向原席位已经表达过的具体内容；
4. 原席位针对质疑回应，不得回避或改换立场；
5. 新出现的外部事实必须有来源；
6. 默认只完成一轮，继续碰撞作为后置增强。

### 5.6 校：确认隐藏分歧

AI 输出 2—3 个候选，候选必须绑定实际碰撞证据，并尽量揭示：

- 风险判断差异；
- 行动时机差异；
- 缓冲方案是否可行；
- 损失是否可逆；
- 双方默认前提差异。

用户可以选择一个、组合多个、修改表述、选择“都不是”。用户拒绝全部候选时，允许直接整理结果，不强迫确认。

### 5.7 请：第三视角为可选增强

第三视角只能从用户确认后的隐藏分歧产生，且必须：

- 不重复前两席；
- 不只是简单折中；
- 说明前两席为何争不拢；
- 提供可执行的判断工具；
- 有充分知识支持时才展示来源。

推荐优先使用可验证的视角框架：可逆性与选择权、风险承受能力、信息价值、最小可行试错、行动触发线。

第三席预览包含：名称、生成依据、问题重构、判断工具、来源或“来源不足”说明。

用户可：

- 邀请第三席入桌；
- 换一个视角；
- 不邀请，直接整理。

第三席生成失败、来源不足或用户不邀请时，均必须正常进入结果页。

第三席生成前置条件：碰撞点已拖动确认、质疑与回应均已完成、隐藏分歧候选已生成，且用户已确认或修正一个隐藏分歧。不满足任一条件，不得调用第三席生成接口。

### 5.8 留：记录离桌理解

离桌表达可选，支持快速选择或自由输入：

- 更确定原来的倾向；
- 开始倾向另一席；
- 结论没变，但理由变了；
- 仍然没有确定答案；
- 原来的问题问得不够准确；
- 跳出了原来的二选一；
- 自己表达。

用户可以跳过。系统不得推测用户未明确表达的情绪、立场变化或确定程度。

## 6. Agent 上下文契约

每次 Agent 调用都必须接收结构化上下文，而不是依赖模型自行记忆前文。

```text
session:
  sessionId
  requestId

topic:
  topicId
  title
  question

currentSeat:
  seatId
  seatName
  role
  stance
  boundaries

conversation:
  firstSeatStatement
  secondSeatStatement
  followups[]
  userAddedConditions[]
  firstTendency
  selectedCollisionPoint
  challenge
  response
  confirmedDivergence

evidence:
  retrievedSources[]
```

硬性规则：

- 当前席位必须知道自己是谁；
- 用户最新问题必须单独突出；
- 历史对话按时间顺序传入；
- 另一席内容只能作为讨论上下文，不能被冒充为当前席位来源；
- 检索结果是证据，不是最终回答；
- Skill 可以规定检索或回答行为，但不能替代上下文注入和生成调用。

## 7. 检索、生成与校验

每个需要回答的环节都遵循：

```text
识别用户新增情境
  ↓
限定 topicId + seatId 检索
  ↓
注入当前席位 Prompt
  ↓
读取本桌上下文
  ↓
调用 chat/completions 生成
  ↓
校验席位、来源和问题相关性
  ↓
展示 reply + 来源
```

模式必须区分：

- `generated`：检索证据后由聊天模型生成；
- `retrieval`：仅返回来源摘录，仅可作为明确标注的降级结果；
- `fallback`：无 API 或调用失败时的规则兜底。

追问、碰撞回应、第三视角和总结不得把 `retrieval` 伪装成 `generated`。

## 8. 席位一致性不变量

任一追问结果必须同时满足：

> 回答席位正确、来源席位正确、回答问题正确。

接口请求至少包含：

```text
topicId
seatId
sessionId
requestId
question
```

接口响应至少包含：

```text
topicId
seatId
requestId
reply
sourceIds[]
sourceSeatIds[]
mode
```

校验要求：

- `sourceSeatIds` 必须全部等于请求中的 `seatId`；
- 前端展示席位、请求 `seatId`、响应 `seatId` 必须一致；
- 席位切换时清空旧回答；
- 只接受最新 `requestId` 的响应；
- 旧请求不得覆盖新请求；
- 发生席位校验失败时，返回当前席位安全兜底，不返回另一席内容。

## 9. 证据分层

| 证据类型 | 用途 |
| --- | --- |
| 外部知识证据 | 支撑事实、研究结论和经验材料 |
| 席位立场证据 | 支撑行动派或现实派的具体判断 |
| 本桌对话证据 | 支撑碰撞点、隐藏分歧、地图和金句 |
| 用户表达证据 | 支撑用户倾向与离桌理解 |

每个生成结果应尽可能记录：

```text
evidenceType
sourceIds[]
conversationQuoteIds[]
seatId
```

隐藏分歧、讨论地图和灵魂金句主要依赖本桌对话证据，不得为了满足“有知乎来源”而硬贴无关来源。

## 10. 最终产物

### 10.1 讨论地图

固定结构：

- 中心问题：1 个；
- 外围发现：最多 3 个；
- 用户轨迹：1 条；
- 外围节点建议 4—6 个字；
- 不出现长段落。

邀请第三席时，外围发现可包含第三席实际产生的新视角；不邀请时，只能使用前两席碰撞、确认后的隐藏分歧、未解问题和用户轨迹，不得标记为第三席观点。

### 10.2 灵魂金句

- 每桌 1 句；
- 建议 18—32 字；
- 只能来自实际发生的讨论；
- 不输出泛化鸡汤；
- 不替用户作最终决定；
- 第三席未入桌时不得引用第三席候选视角作为既成结论。

### 10.3 结果页

```text
本桌议题
  ↓
讨论地图
  ↓
灵魂金句
  ↓
查看知乎来源
  ↓
截图 / 分享
```

第三席是否入桌不改变结果页布局。

## 11. 失败与降级路径

- 两席观点差异不足：提示“当前差异有限”，允许直接整理；
- 合格碰撞点不足两个：允许只展示一个；
- 用户否定全部碰撞点：允许自由输入或直接整理；
- 用户否定全部隐藏分歧：直接生成简版结果；
- 来源不足：明确标注“现有材料不足以判断”；
- 第三席生成失败：跳过第三席，继续结果页；
- API 超时：使用明确标注的 fallback；
- 用户中途退出：基于已完成内容生成简版地图；
- 追问涉及严重健康、债务或危机：只提供一般信息和求助建议，不替用户做医疗或财务决定。

## 12. Demo 范围收敛

### 12.1 必须实现

- 一个预设话题：年轻人该不该裸辞；
- 两个初始席位及独立发言阶段；
- 每席核心观点、边界和来源；
- 每席一轮追问；
- 三个首次倾向选项；
- 2—3 个 AI 动态生成或可验证的碰撞点候选；
- 选择一个碰撞点并拖到两席中间触发碰撞；
- 一轮质疑—回应；
- 2—3 个隐藏分歧候选及用户确认 / 拒绝；
- 第三视角预览的可选入口；
- 不邀请第三席时正常生成结果；
- 讨论地图、灵魂金句和来源索引；
- 席位校验、请求 ID 和基础回归测试。

### 12.2 后置能力

- 完全开放话题；
- AI 从零动态发现碰撞点；
- 无限多轮辩论；
- 主持人自由梳理；
- 多个第三视角并行比较；
- 长期账户、历史和社交系统；
- 复杂交互式知识图谱。

## 13. 验收标准

### 产品流程

1. 第一席和第二席以独立阶段依次出现；
2. 用户可追问任一席，结束后回到对应主流程锚点；
3. 首次倾向只有三个选项；
4. 用户可从 2—3 个候选中选择一个具体碰撞点；
5. 用户将碰撞点卡片拖到两席中间后，系统才触发碰撞；
6. 另一席围绕该点先质疑，原席位具体回应；
7. 用户可确认、修改或拒绝隐藏分歧；
8. 只有隐藏分歧确认后才生成第三席预览；
9. 第三席可跳过，跳过后仍能完成结果页；
10. 用户离桌表达可跳过。

### 上下文与质量

9. 用户问“如果孩子生病了呢”时，回答必须明确处理该新增条件；
10. 每个回答都能说明当前话题、当前席位和用户最新问题；
11. 追问回答不能直接等于某条来源的原文截取；
12. 来源不足时不得强行拼接无关内容；
13. 碰撞点和隐藏分歧都能回溯到本桌对话证据。

### 席位与安全

14. action 请求只能返回 action 来源，realist 请求只能返回 realist 来源；
15. 页面席位、请求 `seatId`、响应 `seatId` 三者一致；
16. 并发追问时旧请求不能覆盖新请求；
17. 第三席未正式邀请时，不得写成已参与讨论；
18. 用户未表达的心理变化不得写入结果。

### 体验与性能

19. 不邀请第三席的最短路径控制在 3—5 分钟；
20. 单次生成最好在 3 秒内返回，超时需有加载反馈；
21. 任一步失败都能基于已发生内容生成简版结果；
22. 用户能区分外部来源、AI 归纳和自己的表达。

## 14. 对外表达

### 30 秒介绍

> 知识拼桌先让你听两个来自知乎真实内容的不同观点，也可以分别追问。听完后，你选择一个当前倾向，再挑一个刚才真正发生冲突的问题，让两席围绕它完成一次质疑和回应。AI 从这次碰撞里找出隐藏分歧，由你确认是否准确；第三视角可以邀请，也可以跳过。最后你会带走一张只记录真实讨论的地图和一句属于这桌的灵魂金句。

### 最短版本

> 听两个真实观点，问一问，挑一个真正值得碰的问题；AI 帮你拆出隐藏分歧，第三视角可请可不请，最后带走一张讨论地图和一句灵魂金句。

### 核心产品逻辑

> 每次回答都必须知道当前话题、当前席位、用户最新问题和本桌上下文。检索结果只能作为证据，不能直接替代回答。席位身份必须从前端请求、后端检索、Agent Prompt 到最终展示全链路一致。第三席是增强项，不能成为主流程成功的前提。

## 15. 产品目标与非目标

### 15.1 产品目标

- 让用户在 3—5 分钟内听懂两个有依据的不同判断；
- 让用户主动选择一次真正具体的观点碰撞；
- 让用户看见表面立场背后的风险、前提或时机差异；
- 让用户带走对自己有帮助、但不替自己决策的结果；
- 证明“结构化碰撞”比单次 AI 问答更能产生认知价值。

### 15.2 非目标

- 不提供医疗、法律或财务上的确定性决策；
- 不模拟真实知乎答主本人；
- 不追求无限轮辩论；
- 不在 Demo 阶段建设账户、社区、积分和长期知识库产品；
- 不把用户引导到预设结论。

## 16. 状态机与状态转移

```text
home
  → intro
  → first-seat
  → second-seat
  → tendency
  → collision-point
  → collision-drag
  → collision-response
  → divergence
  → result

perspective-preview、third-seat 为可选增强状态，任何状态均可安全回到 result。
followup 为覆盖在 first-seat / second-seat 上的临时子状态，结束后回到原状态。
```

### 16.1 状态进入条件

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| `home` | 用户尚未开始 | 点击进入话题 |
| `intro` | 话题已加载 | 点击开始 |
| `first-seat` | 话题和第一席来源就绪 | 第一席展示完成 |
| `second-seat` | 第一席完成 | 第二席展示完成 |
| `tendency` | 两席均完成 | 用户选择三选一 |
| `collision-point` | 首次倾向已记录 | 用户选择或输入碰撞点 |
| `collision-drag` | 已选择碰撞点 | 卡片拖到两席中间并触发碰撞 |
| `collision-response` | 碰撞点有效 | 质疑和回应均完成 |
| `divergence` | 碰撞内容完整 | 用户确认、修改或拒绝 |
| `perspective-preview` | 用户确认隐藏分歧 | 邀请、换视角或跳过 |
| `third-seat` | 用户明确邀请 | 第三席发言完成 |
| `result` | 已有足够讨论记录 | 重置或离开 |

### 16.2 会话状态最小字段

```ts
type SessionState = {
  sessionId: string;
  topicId: string;
  stage: Stage;
  firstSeatStatement?: SeatStatement;
  secondSeatStatement?: SeatStatement;
  followups: FollowupRecord[];
  tendency?: "closer_first" | "closer_second" | "undecided";
  selectedCollisionPoint?: CollisionPoint;
  collision?: CollisionRecord;
  divergences: DivergenceCandidate[];
  confirmedDivergence?: string;
  perspective?: PerspectivePreview;
  thirdSeatInvited: boolean;
  exitUnderstanding?: string;
  updatedAt: string;
};
```

{

  "title": "年轻人该不该裸辞？",

  "riskNotice": "涉及健康、家庭和财务时，仅供参考。"

### 17.2 来源字段

来源必须保留：

- `contentId`；
- `title`；
- `author`；
- `contentText`；
- `url`；
- `voteUpCount`；
- `authorityLevel`；
- `topicId`；

`seatId` 不得依赖数组位置推断，检索结果对象必须显式携带。

### 17.3 内容标注

- 知乎来源；

## 18. API 契约

### 18.1 追问接口

`POST /api/followup`

请求：

```json
{
  "sessionId": "sess_xxx",
  "requestId": "req_xxx",
  "topicId": "T01",
  "seatId": "action",
  "question": "如果孩子生病了呢？",
  "context": {
    "previousFollowups": [],
    "userAddedConditions": []
  }
}
```

响应：

```json
{
  "sessionId": "sess_xxx",
  "requestId": "req_xxx",
  "topicId": "T01",
  "seatId": "action",
  "reply": "……",
  "sourceIds": ["source_1"],
  "sourceSeatIds": ["action"],
  "mode": "generated"
}
```

### 18.2 碰撞接口

`POST /api/collision`

必须传入：`sessionId`、`requestId`、`topicId`、被选中的原席位、碰撞点、两席发言和用户补充条件。

响应必须分别返回：

- `challenge.seatId`；
- `challenge.reply`；
- `response.seatId`；
- `response.reply`；
- 双方各自的来源字段；
- `conversationQuoteIds`。

### 18.3 隐藏分歧接口

`POST /api/divergence`

输入必须包含碰撞点、质疑、回应和用户补充条件。输出 2—3 个候选，每个候选包含：

```json
{
  "id": "irreversible-loss",
  "title": "哪种损失更难恢复",
  "detail": "……",
  "conversationQuoteIds": ["quote_1", "quote_2"]
}
```

### 18.4 总结接口

`POST /api/summary`

总结接口必须允许缺少第三席，也必须允许缺少离桌表达。至少接收：两席内容、碰撞记录、隐藏分歧、用户首次倾向、用户离桌表达和第三席实际发言（如有）。

## 19. Agent 行为规范

### 19.1 席位 Agent

席位 Agent 必须：

- 只使用当前席位身份回答；
- 先回应用户最新问题，再展开背景；
- 不把另一席的观点说成自己的观点；
- 不制造来源中不存在的事实；
- 在无法判断时表达限制；
- 不做命令式最终决策。

### 19.2 主持人 Agent

主持人只负责：

- 告知当前阶段；
- 连接用户和席位；
- 复述已经发生的分歧；
- 帮助用户选择下一步；
- 生成结构化归纳。

主持人不得替用户判断“你其实应该辞职”。

### 19.3 结果生成器

结果生成器只能从会话记录中生成地图和金句。每个外围节点必须至少绑定一条对话证据、用户表达或第三席实际发言。

## 20. 异常处理与可观测性

### 20.1 用户侧提示

- 加载中：显示当前动作，例如“正在查找行动派相关内容”；
- 超时：显示“回答生成较慢，你可以继续整理已发生的讨论”；
- 来源不足：显示“现有材料不足以判断这个情境”；
- 失败：提供“重试”和“直接整理”两个选项。

### 20.2 服务侧日志

每次调用记录：

- `sessionId`；
- `requestId`；
- `topicId`；
- `seatId`；
- 实际检索到的 `sourceIds` 与 `sourceSeatIds`；
- 模式 `generated / retrieval / fallback`；
- 模型耗时；
- 是否发生校验失败；
- 是否触发降级。

日志不得记录 API Key 或不必要的敏感个人信息。

## 21. 埋点与评估指标

### 21.1 核心漏斗

- `topic_enter`：进入话题；
- `first_seat_complete`；
- `second_seat_complete`；
- `tendency_selected`；
- `collision_selected`；
- `collision_complete`；
- `divergence_confirmed`；
- `perspective_invited`；
- `result_generated`；
- `result_shared`。

### 21.2 质量指标

- 两席完成率；
- 碰撞点选择率；
- 结果页到达率；
- 追问回答相关性评分；
- 席位串位率，目标为 0；
- 来源席位校验失败率，目标为 0；
- 用户认为“碰撞点来自刚才讨论”的比例；
- 用户能否说出两席核心差异；
- 平均完成时长，目标 3—5 分钟。

## 22. 安全与内容边界

- 不冒充具体知乎答主；
- 引用内容保留原作者与链接；
- 对健康、债务、家庭危机等内容增加一般性提示；
- 不收集与流程无关的身份证、联系方式和精确财务信息；
- 用户补充的个人条件只用于当前会话，Demo 不做长期保存；
- 任何模型生成内容都必须允许用户看到其证据边界。

## 24. Demo 验收脚本

使用话题“年轻人该不该裸辞”，依次验证：

1. 进入话题后先看到第一席，再看到第二席；
2. 点击行动派追问“如果孩子生病了呢”，回答明确提及孩子照护或家庭责任；
3. 点击现实派追问同一问题，回答保持现实派的现金流和保障立场；
4. 检查两次响应的 `seatId` 和 `sourceSeatIds` 均正确；
5. 快速连续发起两次追问，最终页面只展示最后一次结果；
6. 完成三选一倾向记录；
7. 选择一个具体碰撞点；
8. 仅点击碰撞点不触发碰撞，拖到两席中间后才触发质疑—回应；
9. 在未完成碰撞或未确认隐藏分歧时，第三席生成接口不可被调用；
10. 拒绝全部隐藏分歧，确认仍可进入结果页；
9. 不邀请第三席，结果页不出现“第三席已发言”；
10. 邀请第三席，结果页只纳入第三席实际发言；
11. 检查地图最多三个外围节点，金句来自本桌实际讨论；
12. 断开 API 或模拟超时，仍可生成标注为降级的简版结果。
