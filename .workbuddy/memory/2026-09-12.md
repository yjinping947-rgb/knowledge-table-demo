## npm install / next dev 的两个副作用（已还原）

跑完依赖和 dev server 后 `git status` 出现两个非预期改动，**已用 `git restore` 还原，工作区现为干净**：

1. `next-env.d.ts`：Next 自动生成（文件头写着 "This file should not be edited"）。dev 模式下把 `.next/types/*` 改写成 `.next/dev/types/*`。**每次跑 dev/build 都会重现，属正常现象**，不是谁改坏了。
2. `package-lock.json`：90 行删除，全是 `"libc": ["glibc"]` 字段。原因是本机 npm 是 **10.9.7**（随托管 Node 22），而队友生成 lock 用的是更新版 npm（Node 24 自带的 npm 11+），新版本才会写 `libc` 字段。旧 npm 重写 lock 就把这些字段抹掉了。纯元数据差异，不影响安装结果。

**教训**：`npm install` 不只是"装 node_modules"，它可能重写 lockfile；`next dev` 会改 `next-env.d.ts`。做完要 `git status` 查一遍再交付。

## 切到 dev-lhq 并跑起来

**用户症状**：「打开网址还是最老的版本」
**根因**：dev server 是用 `main` 的工作区文件启动的。**切分支不会让已跑着的服务换内容，必须停掉重启。** 这是纯操作问题，不是配置问题。

**操作序列（已验证可复现）**
```bash
# 1. 停掉旧服务（TaskStop 或 Ctrl+C）
# 2. 切分支（本机必须补 reset --hard）
git checkout dev-lhq && git reset --hard dev-lhq

npm run dev
```

**dev-lhq 比 main 多的 4 个 devDependencies**（运行依赖 5 个完全相同）
`@commitlint/cli` `@commitlint/config-conventional` `husky` `lint-staged`

### ⚠️ 关键限制：RAG 聊天完全依赖 AI key，无 key 时检索根本不跑
- `src/lib/rag/client.ts` 的 `embedQuery()`：无 `AI_API_KEY`/`AI_BASE_URL` 时**直接 return null**
- `src/lib/rag/pipeline.ts` 第 2 步：`if (!queryVec) return { answer: fallbackAnswer, retrieved: [], mode: "fallback" }`
- 实测结果：`POST /api/answer {question:"我该听你的建议吗？",roomId:"r01",k:3}`

## 语料的采集管道（用户问"是本地存储还是调知乎 API"）

**答案：100% 提前固化在本地，运行时完全不碰知乎。** 逐行核实：

### 运行时代码零知乎调用
`grep -rn "zhihu|知乎" src app` 的 12 处命中**全是注释和界面文案**（"真实知乎答主"、"查看原文 ↗"），无一处网络请求。
运行时全部网络出口只有 3 个，**全部指向 `AI_BASE_URL`（阿里云百炼）**：
- `src/lib/ai/client.ts:12` — `new OpenAI(...)`
- `src/lib/rag/client.ts:19` — `new OpenAI(...)`（embedding）
- `src/lib/rag/pipeline.ts:129` — `fetch(\`${baseURL}/chat/completions\`)`

### 采集脚本（离线，一次性）
`scripts/collect-corpus-batch.mjs`：
- 调用**本地 CLI**：`C:\Users\HUAWEI\AppData\Local\ZhihuCLI\current\zhihu-cli.exe`
- `zhihu-cli.exe search zhihu --query "<关键词> <修饰词>" --count 10`
- 20 话题 × 3 派 × 2 次查询 = **120 次 search**，去重后 `writeFile` 到 `src/data/topics.json`
- 提取字段：ContentID/Title/AuthorName/ContentText/Url/VoteUpCount/CommentCount/AuthorityLevel

⚠️ **该 CLI 路径在用户机器上不存在**（`/c/Users/HUAWEI/` vs 用户的 `/c/Users/lenovo/`）→ **采集脚本在用户电脑上跑不了**，是队友在自己机器上跑完把 JSON 提交的。

### ⚠️⚠️ 发现严重的语料标签质量问题
`collect-corpus-batch.mjs` 的"三派"标签是**靠搜索词后缀粗分**的，不是语义分类：
```js
const SEATS = [
  { id: "action",      mods: ["立刻","立即","马上","必须"] },
  { id: "realist",     mods: ["现实","风险","代价","经济"] },
  { id: "conditional", mods: ["条件","看情况","策略","前提"] },
];
const queries = [`${t.keywords[0]} ${s.mods[0]}`, t.keywords[1] ?? t.keywords[0]];
```
**第二个查询 `keywords[1] ?? keywords[0]` 对三个派别完全相同** → 同一批通用结果会被三个派别都收进去（槽位内去重，不跨派别去重）。

实测后果：
- 全库 contentId 去重后 **753 条**（1184 是含重复的槽位数）
- **229 条（30.4%）同时出现在多个派别里**
- T01「裸辞」action 20 条中，**12 条**与 realist/conditional 重复
- **语义反例**：「脑子一热就裸辞！90%后悔的人，都栽在这一步」同时被标为 action（行动派=鼓励行动）和 conditional —— **标签与内容语义相反**

**影响**：`/api/discuss` 用 `retrieveFromTopics({topicId, seat})` 按 seat 检索 → 行动派席位可能召回一条"90%后悔"的内容，说出反对自己立场的话。这是直接损害产品体验的缺陷，也是 agent-dev 该修的东西。
