## 一、GitHub 团队协作的心智模型

### 1.1 两个仓库，一条规则

你的电脑上有一份仓库，GitHub 上有一份。两者的关系是：

```
你的电脑                           GitHub
├── main ────────── push ────────▶ origin/main   （受保护）
└── feat/xxx ────── push ────────▶ origin/feat/xxx
     ▲                                    │
     └───────────── pull ─────────────────┘
```

**关键规则**：`main` 是所有人的共识版本，**不要直接改**。你的改动永远先落在自己的分支上，通过 PR 汇入 `main`。

> 注意：`main` 受保护是**配置出来的**，不是 git 本身的属性。如果仓库没配分支保护，Write 权限的人技术上能直推 main —— 但那是破坏约定的行为。

### 1.2 什么是 Pull Request

**PR 不是 git 的功能，是一个社交容器。** 它把三件事打包在一起：

1. **请求** —— "我这有个改动，请合并"
2. **评审** —— 别人可以逐行评论
3. **记录** —— 为什么改、谁批的、跑了什么测试，永久留在历史里

git 只管"代码怎么合"，PR 管"凭什么合"。这就是团队协作和单人开发最大的差别。

### 1.3 你必须记住的命令

```bash
cd "D:\知乎黑客松团队知识拼桌项目"

# 1. 站到主干并更新
git checkout main && git reset --hard main && git pull

# 2. 开自己的分支（名字格式有强制要求，见 3.2）
git checkout -b feat/corpus-add-topic

# 3. 改完代码后提交
git add .
git commit -m "feat(corpus): 补一条话题条目"

# 4. 推上去
git push -u origin feat/corpus-add-topic

# 5. 在 GitHub 网页上开 PR（Compare & pull request）
```

> ⚠️ **本机特有的坑**：这台电脑上 `git checkout` 切换分支会「吞文件」（详见第六节）。所以每次切分支后都要补一刀 `git reset --hard <分支名>` 来重建工作区。

### 1.4 你们仓库的 4 道关卡

提交一个 PR，要依次过：

| 顺序 | 关卡 | 配置文件 | 不过会怎样 |
|---|---|---|---|
| 1 | 本地钩子：lint + test | `.husky/pre-commit` + `.harness/hooks/` | commit 被拒 |
| 2 | 本地钩子：commit 格式 | `.commitlintrc.json` + `.husky/commit-msg` | commit 被拒 |
| 3 | 云端：分支名格式 | `.github/workflows/branch-name.yml` | PR 红叉，合不了 |
| 4 | 云端：lint + build + 测试 | `.github/workflows/ci.yml` | PR 红叉，合不了 |
| 5 | 人工：CODEOWNERS 指派 review | `.github/CODEOWNERS` | 没人 approve 就合不了 |

## 二、项目现状

### 2.1 两个分支，差了一个大版本

| | `main` | `dev-lhq`（队友的） |
|---|---|---|
| 版本 | 0.1.0 单体 Demo | 1.3.0 完整工程 |
| 文件数 | 27 | 198 |
| 交互 | 单话题「该不该裸辞」两轮讨论 | 20 个房间，每房间一条知乎问答 |
| AI | 3 个观点席位 + 兜底 | 同上 + 本地 RAG 向量检索 |
| 目录 | `lib/` `app/` `components/` | `src/{agents,client,lib,data,user}` |
| 治理层 | 无 | `.harness/` + `docs/` + `.github/` |
| 测试 | `tests/core-branches.mjs` | 再加 `tests/rooms-rag.mjs` |

> `dev-lhq` 是 `main` 的超集方向 —— 它把 Demo 工程化了，并补上了团队协作的全套设施。

### 2.2 架构：5 个 AI 角色

```
user（用户选择）
      │
      ▼
  director（导演）───── 决定"这一轮让哪个席位发言"
      │
      ├──▶ action（行动派）        健康止损立场，绑来源 S01-S03
      ├──▶ realist（现实派）       经济安全立场，绑来源 S04-S06
      └──▶ conditional（条件派）   条件判断立场，绑来源 S07-S09
      │
      ▼
  fallback（统一兜底）──── 缺 key / 超时 / 解析失败 / 来源越界
```

**兜底是硬要求**：任何 AI 调用路径都必须能在没有 API key 的情况下产出内容。这正是你现在跑的"演示模式"。

### 2.3 三套角色，别搞混

| 层 | 是什么 | 在哪 | 有几个 |
|---|---|---|---|
| AI 角色 | 代码里的运行时契约 | `.harness/agents/` + `src/agents/` | 5（director/action/realist/conditional/user） |
| human 角色 | 人的开发职责 | `.harness/roles/` | 4（agent-dev/ui-design/feature-design/corpus） |
| GitHub team | PR 的 review 路由 | `.github/CODEOWNERS` | 4 + maintainers 兜底 |

**三层互相独立**：改 AI 角色不影响 review 路由；GitHub team 没建，代码照样能跑。

### 2.4 治理层（`.harness/`）是什么

这是这个仓库最特别的地方 —— 它**把「人」和「AI」当成同一种贡献者来规范**，对标 [agents.md](https://agents.md/) 规范。

`.harness/INDEX.md` 是**单一事实源**：改任何 `.harness/` 下的文件前，先看它。

## 三、未来怎么开发

### 3.1 第一步：认领一个 human 角色

**这是你该问队长的第一个问题：我负责哪块？**

| 角色 | 负责目录 | 关键 skill | 适合谁 |
|---|---|---|---|
| `agent-dev` | `src/agents/` `src/lib/{ai,rag,prompts,fallback,validators}` `app/api/` | commit-with-rationale | 写后端 / AI 逻辑 |
| `ui-design` | `src/client/` `components/` + 4 个冻结资源 | commit-with-rationale | 写界面 |
| `feature-design` | `app/api/` `.harness/contracts/` `tests/` `.github/workflows/` | commit-with-rationale + deploy-app | 定接口 / 写测试 |
| `corpus` | `src/data/` `scripts/` | add-corpus + commit-with-rationale | 收集整理语料 |

定义详见 `.harness/roles/<角色>.md`。

### 3.2 改代码的标准流程

来自 `docs/development/workflow.md`，浓缩成 12 步：

```
读治理层 → 拉分支 → 写"变更前预期" → 改代码
                                        ↓
                            跑 lint + build + test
                                        ↓
                        写"变更后端测效果" + change report
                                        ↓
                          commit → push → PR
                                        ↓
                              review + CI
                                        ↓
                                    merge
                                        ↓
                                  同步文档
```

**分支名硬性格式**：`<type>/<scope>-<短描述>`

- `type` 只能是：`feat` `fix` `refactor` `test` `docs` `chore` `style` `perf` `ci` `revert`
- 全小写、连字符分隔，≤60 字符
- 例：`feat/client-add-copy-button`、`fix/director-router-fallback`

**commit 硬性格式**：`<type>(<scope>): <中文简述>`，简述 ≤30 字，用动词开头

**两个灵魂字段**（写在 PR 描述里，这是队里最看重的）：

- **变更前预期** —— 动手**之前**写下"我预期改完会怎样"，哪怕只 3 行
- **变更后端测效果** —— 改完跑完测试后，写实际结果

### 3.3 4 个核心 skill

|---|---|

## 六、已知的坑（实测发现，非文档记载）

### 6.1 本机 git 切分支会吞文件

在这台电脑上 `git checkout` 在 `main` ↔ `dev-lhq` 之间切换时，会删除 `app/globals.css`、`app/layout.tsx`、`lib/types.ts` 且**不写回**。诱因疑似 `dev-lhq` 引入的 `.gitattributes` 行尾策略（`*.tsx text eol=lf`）与 `main` 无该文件之间的差异。

**解法**：切完分支补一刀强制重建。

```bash
git checkout dev-lhq && git reset --hard dev-lhq
```

### 6.2 CODEOWNERS 里的 team handle 只是占位

`.github/CODEOWNERS` 里写的是 `@MiniMax/agent-dev` 这类 handle，但仓库实际的 remote 是 `github.com/yjinping947-rgb/knowledge-table-demo`，**跟 `MiniMax` 组织对不上**。`CHANGELOG.md` 里的 commit 链接同样指向 `github.com/MiniMax/...`。

**含义**：那 4 个 team 很可能从未真正创建。结果是 PR 不会自动指派 reviewer，需要手动 `@` 真人。

队里留了兜底方案：`node scripts/setup-teams.mjs single-user <你的handle>`，会把所有 team handle 替换成一个具体账号，不调 GitHub API。

### 6.3 npm 版本差异会改 lockfile

本机 npm 是 10.9.7，生成 `package-lock.json` 的队友用的是更新版 npm。跑 `npm install` 会删掉 lockfile 里的 `"libc"` 字段（约 90 行）。纯元数据差异，不影响安装，但会在 `git status` 里显示成改动 —— 记得 `git restore package-lock.json` 还原。

### 6.4 `next dev` 会改 `next-env.d.ts`

Next.js 自动生成的文件，dev 模式把路径从 `.next/types/` 改写成 `.next/dev/types/`。**正常现象**，每次跑 dev 都会发生。不用管，也不要提交。
